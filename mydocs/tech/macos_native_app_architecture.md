# macOS 네이티브 앱 아키텍처 결정과 0단계 스파이크 결과

rhwp-mac 포크가 목표로 하는 "맥 전용 Swift 네이티브 편집기"의 구조 결정과, 그 결정을 뒷받침하는
0단계 스파이크(Rust 레이어 트리를 CoreGraphics/CoreText로 재생) 결과를 기록한다.
이후 단계의 작업 단위와 완료 기준은 [단계별 계획](#단계별-pr-계획)을 따른다.

## 결정

**Rust 엔진을 유지하고, 그 위에 SwiftUI/AppKit 네이티브 앱을 얹는다.**

- 파서·조판·편집 명령·직렬화는 Rust(`DocumentCore`)에 둔다. 약 69.5만 줄이며 한컴 호환 조판 규칙이
  쌓여 있어 Swift로 다시 쓰면 "원본의 핵심 기능 유지"와 충돌한다.
- UI, 문서 수명주기, 페이지 렌더링, 입력(IME), 인쇄/PDF, 시스템 통합은 Swift로 만든다.
- UI는 시스템 컴포넌트(Liquid Glass)만 쓴다. 직접 그리는 영역은 페이지 캔버스뿐이다.
- 최소 지원 OS는 macOS 26이다. (Liquid Glass가 26부터다.)

```
SwiftUI/AppKit 앱
  └ RhwpKit (Swift Package, Swift 6 concurrency, actor 기반 DocumentSession)
      └ CRhwp (XCFramework, 정적 라이브러리)  ← bindings/Native 확장: 핸들 기반 C ABI
          └ Rust 코어 (DocumentCore)
```

## 저장소 정리 방침

이 포크는 업스트림 rhwp에 "맥 호환을 추가"하는 것이 아니다. **macOS 네이티브 앱이 동작하는 데 필요한 것만 남긴다.**
그래서 웹 편집기·브라우저/에디터 확장·Tauri 앱·CI·CLI·에이전트 도구(MCP, 캡슐, RAG, 스킬)·WASM 전용 출력은 지운다.
남기는 것은 엔진(`model`, `parser`, `serializer`, `document_core`, `renderer`, `paint`, `wmf`·`emf`·`eps`, `ole_chart`,
`crates/*`), 앱이 쓰는 C ABI(`bindings/Native`), Swift 앱(`macos/`), 그리고 렌더 충실도 검증의 기준 자료인
`samples`·`pdf`다. 삭제는 git 기록에 남아 되살릴 수 있다.

**에이전트 표면의 기준.** 앱의 편집기·뷰어가 쓰는지로 가른다. 지운 것은 LLM 에이전트가 문서를 읽고 검사하고
채우는 데 쓰던 질의와 자동화다: 프롬프트 주입·위협·개인정보·은닉 문자 탐지(`injection_scan`, `threat_scan`,
`pii_scan`, `hidden_text`, `stego_scan`, `armor`, `text_security`), 주소가 붙은 검색·추출(`grep`, `extract_data`,
`explain`, `explore`, `changed_pages`, `structure`, 표·차트 CSV), 문단 블록 템플릿 자동화(`paragraph_block`),
시험지 빌더, 쪽 범위 추출, 글꼴 측정 커버리지 분석, 그리고 웹한글컨트롤 호환 커서 API(`hwpctrl_sets`)와 그
파사드 래퍼. 글 편집·서식·표·개체·필드·책갈피·하이퍼링크·찾기와 바꾸기·개요 탐색·클립보드(HTML·한컴 문서모델)는 남겼다.

**일부러 남긴 것.** `table_extract`와 `chart_extract`는 속성 테스트(저장 왕복 비교)와 차트 편집이 쓴다. 검색 순회가
같은 범위를 훑으므로, `grep`을 오라클로 쓰던 테스트는 `search_all_text_native`로 옮겨 살렸다. `converters`,
`hwpjson`, `canvas_metrics`(글꼴 측정 외부 공급 프로토콜)도 유지한다.

**죽은 코드 찾는 법.** 루트 `Cargo.toml`이 `dead_code = "allow"`라서 컴파일러는 말해 주지 않는다. 절차는 이렇다.

1. `[lints.rust]`의 `dead_code`를 잠시 `warn`으로 바꾸고, `src/lib.rs`에서 `document_api`를 뺀 최상위 모듈을 `pub(crate)`로
   좁혀 `cargo check --lib --message-format json`을 돌린다. `pub` 항목은 통합 테스트가 쓸 수 있어 좁히지 않으면 경고가
   나오지 않는다. 좁히면 앱이 쓰는 공개 표면(`document_api`, `DocumentCore`, 파싱·저장 함수)에서 닿지 않는 항목이 나온다.
2. 통째 항목(함수·메서드·상수·구조체·열거형·트레이트·타입 별칭)만 후보로 삼는다. 필드와 열거형 변형은 지우면 생성자와
   `match`가 줄줄이 바뀌므로 따로 다룬다.
3. 후보 중 `tests/`·`bindings/`·`crates/`가 **이름을 단어 단위로 참조**하거나, `src/` 안의 단위 시험 코드
   (`#[cfg(test)]`, `tests.rs`, `*_tests.rs`)가 참조하면 뿌리로 남긴다. 뿌리 본문에 이름이 나오는 다른 후보도
   전이적으로 남긴다. 이 폐쇄를 계산하지 않으면 시험이 쓰는 함수의 보조 함수를 지워 컴파일이 수천 줄 깨진다.
4. 나머지를 지우고 컴파일하면 새 후보가 나타난다(지운 항목만 쓰던 것들). 후보가 0이 될 때까지 되풀이한다.
   지운 항목이 `pub use` 목록이나 트레이트 정의에 있었다면 컴파일 오류가 가리키므로 손으로 고친다.
5. 설정을 원래대로 돌리고 `cargo check --workspace --all-targets`로 시험까지 컴파일되는지 확인한다.

**`cargo fix`로 `use` 줄을 한꺼번에 정리하지 않는다.** `unused_imports`를 켜고 `cargo fix --all-targets`를 돌리면
비시험 빌드에서 안 쓰이는 `use`(단위 시험이 `use super::*`로 받아 쓰는 것)까지 지워 lib test가 수십 곳 깨진다.
사양을 옮긴 상수 표(`parser/tags.rs`, `parser/hwp_summary.rs`, 글자 모양 비트 표)와 레이어 트리 계약 상수
(`paint/schema.rs`)는 쓰이지 않아도 남긴다. Swift 모델과 이후 서식 편집 단계가 같은 값을 쓴다.

## 0단계 스파이크

### 질문

Rust가 만드는 레이어 트리(`PageLayerTree`, PaintOp IR) JSON만으로 Swift가 한 쪽을 충실히 그릴 수 있는가?
가능하면 조판을 Swift에서 다시 계산하지 않고 "Rust가 배치, Swift가 그리기" 구조로 갈 수 있다.

### 방법

- `bindings/Native`에 `rhwp_page_layer_tree(path, page)`를 추가했다. 쪽의 레이어 트리 JSON을 돌려준다.
  스파이크용 무상태 표면이며 1단계의 핸들 기반 API로 대체된다.
- 스파이크(`macos/Spikes/PaintOpSpike`, 3단계에서 `RhwpRender`와 `rhwp-render`로 대체되어 지웠다)가 이 JSON을 읽어 CoreGraphics/CoreText로 PNG에 재생했다.
  지원 op: `pageBackground`, `textRun`, `line`, `rectangle`, `ellipse`, `path`, `image`와 `clipRect` 노드.
- 글자는 Rust가 계산한 `positions`(run 기준 글자별 x 오프셋)와 `placement.runToPage`의 원점·기준선에
  한 글자씩 놓는다. 줄 나눔·자간·장평 폭은 엔진 결과를 그대로 따르고 Swift는 글리프만 그린다.
- 기준은 한컴이 출력한 PDF(`pdf/KTX-2022.pdf`, `samples/*.pdf`; Producer `Hancom PDF 1.3.0.550`)이고,
  두 출력을 같은 96dpi×2 래스터로 맞춘 뒤 `scripts/visual_sweep.py --silhouette-only --png-pair`의
  2px 이웃 관용 내용 실루엣 일치율로 쪽별 비교했다. PDF 래스터화는 Quartz(`CGPDFDocument`)로 흰 배경에 했다.

### 결과

| 문서 | 쪽수(Rust / 한컴 PDF) | 최저 | 중앙값 | 90% 미만 쪽 |
| --- | --- | --- | --- | --- |
| `samples/KTX.hwp` | 27 / 27 | 52.0 | 93.3 | 7쪽 (1, 2, 5, 10, 12, 19, 26) |
| `samples/2022년 국립국어원 업무계획.hwp` | 35 / 35 | 66.2 | 88.6 | 22쪽 |
| `samples/21868765_별표2_보건소_분장사무.hwp` | 4 / 4 | 76.1 | — | 1쪽 (1쪽 76.1, 2~4쪽 97.1~98.9) |

- 쪽수는 세 문서 모두 일치했다. HWPX(`2025 행정업무운영 편람`, `2025년 기부·답례품 … 양식`)도 같은 경로로 그려진다.
- 쪽당 재생 시간은 약 10~90ms(릴리스 빌드, JSON 파싱 제외)다.
- 직접 판독한 3쪽(KTX 1·5쪽, 국립국어원 4쪽)의 덮어 그린 그림에서 선·박스·표 괘선·이미지·로고·
  그라데이션 막대·글줄 위치는 PDF와 겹친다. 차이는 글리프 자형과 굵기로 보인다. 한컴 글꼴(`HY헤드라인M`,
  `휴먼명조` 등)이 맥에 없어 `Apple SD Gothic Neo`/`AppleMyungjo`로 대체되기 때문이라고 추정한다.
  나머지 쪽은 직접 판독하지 않았고, 글꼴을 공급해 점수가 오르는지도 확인하지 않았다(미검증).
- 이 점수들은 **실루엣 보조값**이다. 프로젝트 기준 90%를 넘지 못한 쪽이 있으므로 이 스파이크 결과를
  렌더링 정확도 통과로 주장하지 않는다. 스파이크는 접근의 타당성만 입증한다.

### 발견 사항

1. **그라데이션 각도 규칙이 레이어 트리에 풀려 있지 않다.** `angle`만 실리고 축 방향 규칙은 Rust 정본
   (`src/renderer/mod.rs`의 `linear_gradient_axis`: 방향 = (sin θ, −cos θ), θ=90이면 좌→우)에만 있다.
   처음 위→아래로 가정해 한컴 PDF와 방향이 반대로 나왔고, 정본 규칙으로 고쳤다. 소비자마다 같은 규칙을
   복제하게 되므로 Rust가 축 좌표를 직접 내보내는 방안을 2단계에서 검토한다.
2. **dylib는 macOS 27 dyld가 거부한다.** `librhwp_native_ffi.dylib`를 `dlopen`하면
   `mis-aligned LINKEDIT string pool`로 실패한다. 정적 라이브러리(`.a`)를 Swift 링크 단계에 넣는 방식은
   정상 동작한다. 제품은 정적 XCFramework로 간다(1단계에서 구현). (기존 `bindings/swift`가 이름으로 링크하는
   방식이 이 환경에서 dylib를 고르면 같은 문제가 날 수 있으나 확인하지 않았다.)
3. **Rust 정적 라이브러리의 배포 타깃 경고.** Rust를 기본값으로 빌드하면 `blake3_neon.o`가 macOS 27.2용으로
   만들어져 최소 26.0 링크에서 경고가 난다. 빌드 스크립트는 `CFLAGS_aarch64_apple_darwin=-mmacosx-version-min=26.0`을
   지정하고, 그 결과 `blake3_neon.o`의 `minos`가 26.0이 되어 경고가 사라진 것을 확인했다. cc 크레이트는 이 변수가
   바뀌면 빌드 스크립트를 다시 돌린다.
   **`MACOSX_DEPLOYMENT_TARGET=26.0`을 cargo 전체에 걸면 안 된다.** 이 값은 rustc가 만드는 proc-macro dylib
   (`strum_macros`, `snafu_derive`, `zerocopy_derive` 등)의 `minos`도 26.0으로 바꾸고, macOS 27 dyld는 그 dylib를
   위 2번과 같은 `mis-aligned LINKEDIT string pool`로 거부한다. 그러면 컴파일러가 `can't find crate for ...`로
   실패한다. 캐시에 옛 dylib(`minos 11.0`)가 남아 있는 동안은 드러나지 않다가 캐시가 갱신될 때 터진다(#8에서
   발견). 이미 `minos 26.0`으로 만들어진 dylib가 캐시에 있으면 `otool -l <dylib> | grep minos`로 찾아 지운다.

### 재현

```bash
macos/scripts/rhwp-render.sh samples/KTX.hwp 0 /tmp/ktx_p0.png
```

Rust 툴체인(`rust-toolchain.toml`의 1.93.1)이 필요하다. `.json` 확장자를 주면 레이어 트리 원문만 저장한다.
비교용 PDF 래스터화와 실루엣 계산은 위 방법 절의 명령을 따른다.

## 1단계: 핸들 기반 FFI와 XCFramework

0단계의 무상태 함수(`rhwp_page_layer_tree`, 호출마다 재파싱)를 지우고, 열린 문서를 불투명 핸들로 돌려주는
C ABI로 바꿨다. 정본 구현은 `bindings/Native/src/lib.rs`, 정본 헤더는 `bindings/Native/include/rhwp_native.h`다.

| 함수 | 역할 |
| --- | --- |
| `rhwp_document_open(path, &err)` / `rhwp_document_open_bytes(data, len, &err)` | 문서를 열어 핸들을 돌려준다. 실패하면 `NULL`과 오류 JSON(`err`). 성공하면 `*err`는 `NULL` |
| `rhwp_document_page_count(doc)` | 쪽수. 널 핸들·poison된 문서는 -1 |
| `rhwp_document_page_layer_tree(doc, page)` | `{"ok":true,"pageCount":N,"page":P,"layerTree":{...}}` 또는 오류 봉투 |
| `rhwp_document_free(doc)` | 핸들 해제(널 무시) |
| `rhwp_string_free(s)` | 돌려받은 모든 문자열(`err` 포함) 해제 |

- **소유권:** 핸들과 문자열은 호출자 소유이며 각각 한 번만 해제한다. `open_bytes`는 호출 안에서 바이트를 복사한다.
- **동시성:** 핸들은 스레드 안전을 약속하지 않는다. Swift의 actor가 호출을 직렬화해야 한다. 내부 `Mutex`는
  실수로 동시에 호출해도 데이터 경쟁을 막는 안전장치다.
- **panic:** C 쪽으로 풀려나가지 않고 오류 봉투로 바뀐다. 잠금 **바깥**에서 잡기 때문에 `Mutex`가 poison되고,
  이후 호출은 손상됐을 수 있는 문서를 다시 쓰지 않고 오류를 돌려준다(문서를 다시 열어야 한다).
- **헤더:** `cbindgen` 대신 수작업 헤더를 쓰고, `header_declares_exactly_the_exported_symbols` 테스트가
  헤더 선언과 내보낸 `extern "C"` 함수 집합이 같은지 비교한다. 의존성을 늘리지 않으면서 어긋남만 막는 선택이며,
  함수가 늘어 수작업이 부담되면 `cbindgen`을 재검토한다. 선언 하나를 지워 이 테스트가 실패하는 것을 확인했다.
- **Swift 쪽 형태:** 불투명 구조체 `RhwpDocument *`는 Swift에서 `OpaquePointer`로 들어온다. 2단계의 `RhwpKit`은
  이를 `final class`/`actor`로 감싸 `deinit`에서 `rhwp_document_free`를 부른다.

`macos/scripts/build-xcframework.sh [--smoke]`가 정적 라이브러리를 `macos/build/RhwpNative.xcframework`로
묶는다(Apple Silicon 슬라이스 하나, C 객체의 최소 OS는 `CFLAGS_aarch64_apple_darwin`으로 26.0). 모듈은 `CRhwp`이며 `--smoke`는 이
XCFramework를 Swift로 링크해 열기·쪽수·레이어 트리·범위 밖 오류·바이트 열기·널 처리를 실제로 실행한다
(`macos/scripts/ffi_smoke.swift`). 스파이크도 이제 이 XCFramework를 SwiftPM `binaryTarget`으로 소비하며,
0단계와 같은 샘플 쪽을 픽셀 단위로 동일하게 그린다.

범위 밖(후속 단계): 암호 걸린 문서(`from_bytes_with_password`)·편집·저장 API, Intel/유니버설 슬라이스(10단계).

## 2단계: RhwpKit Swift 패키지

`macos/RhwpKit`(Swift 6.2, macOS 26, Swift 6 언어 모드)이 1단계 XCFramework(`binaryTarget` `CRhwp`)를 감싼다.
테스트는 `macos/scripts/test-rhwpkit.sh`(XCFramework를 증분 빌드한 뒤 `swift test`)로 실행한다.

**공개 API**

| 타입 | 역할 |
| --- | --- |
| `RhwpDocumentSession` (actor) | `open(contentsOf:)`, `open(data:)`, `pageCount()`, `layerTree(page:)`, `layerTreeJSON(page:)` |
| `PageLayerTree` / `LayerNode` / `GroupKind` | 한 쪽의 레이어 트리 Decodable 모델 |
| `PaintOp` 및 `TextRunOp`, `RectangleOp`, `ImageOp` 등 | 그리기 명령. 모르는 op는 `.unsupported(type:)`로 보존 |
| `RhwpError` | `openFailed`, `pageOutOfRange`, `documentUnavailable`, `native`, `malformedResponse` |

**설계 결정**

- **문서마다 전용 직렬 큐 위의 actor.** 모든 네이티브 호출이 한 스레드에서 일어나고 협력 스레드 풀을 막지 않는다.
  파싱도 같은 큐에서 한다. `dispatchPrecondition(.onQueue)`로 실행자 연결이 빠지면 즉시 멈추게 했다.
  Rust 쪽이 스레드를 옮겨도 결과가 같음을 1단계에서 보장했으므로 이 구조가 그 계약에 기대는 것은 아니다.
- **핸들 수명은 Swift 참조 수명에 묶는다.** `NativeDocumentHandle`이 마지막 참조가 사라질 때 `rhwp_document_free`를 부른다.
- **파일은 Swift에서 읽어 `open_bytes`로 넘긴다.** 샌드박스·파일 코디네이션과 맞고, 읽기 실패를 Swift 오류로 보고한다.
- **구분이 필요한 오류만 전용 케이스로 만든다.** 범위 밖 쪽은 Swift에서 먼저 검사해 `pageOutOfRange`로 돌려주고,
  엔진 메시지(사람이 읽는 문장)는 문자열로 분기하지 않고 `.native`로 전달한다.
- **스키마가 바뀌면 크게 실패한다.** 주 버전·좌표계(`page-top-left-y-down`)·단위(`px`)가 다르면 잘못 그리는 대신
  디코딩이 `malformedResponse`로 실패한다. 반대로 열거형의 모르는 값(`StrokeDash` 등)은 안전한 기본값으로 낮춘다.
- **글자 위치 계약을 모델에 문서화했다.** `TextRunOp.positions[i]`는 run 원점에서 i번째 유니코드 스칼라의 시작 x이고
  개수는 스칼라 수 + 1이다. 렌더러는 줄 나눔·자간을 다시 계산하지 않는다. `displayText`가 있으면 그것을 그린다.
- **그라데이션 축 규칙은 `Gradient.linearAxis(in:)`에 한 번만 구현했다.** 0단계에서 방향을 잘못 가정했던 규칙이다.

**검증**

- 18건의 Swift Testing 단위 테스트가 통과한다. 기대값은 한컴 PDF(KTX 27쪽, 보건소 4쪽)와 A4 규격(793.70×1122.52px)처럼
  엔진과 독립인 값으로 정했다. 모든 쪽에서 op 종류별 개수를 원본 JSON을 `JSONSerialization`으로 따로 센 값과 대조한다.
- 일부러 결함을 넣어 테스트가 실패하는지 확인했다: leaf의 마지막 op 누락, `positions` 마지막 값 누락, 그라데이션 y 부호 반전,
  좌표계 검사 제거. 모두 검출됐고 원본은 복원했다.
- 임시 스윕(커밋하지 않음): 6MB 이하 샘플 문서 364개의 앞 4쪽씩 847쪽을 디코딩해 실패 0건이었다.
  열기에 실패한 3건은 모두 암호 문서(`*password-123456*`)이며 `openFailed`로 돌아온다(암호 입력 API는 후속 단계).

**샘플에서 관찰된 op 종류와 모델 상태**

| 상태 | op |
| --- | --- |
| 모델링·실데이터 확인 | `pageBackground`, `textRun`, `line`, `rectangle`, `ellipse`(`hwp3-curve.hwp`), `path`(`KTX.hwp` 2쪽), `image` |
| 보존만 함(`.unsupported`) — 4단계 렌더러 범위 | `textDecoration`, `tabLeader`, `charOverlap`, `equation`, `footnoteMarker`, `formObject`, `glyphOutline`, `rawSvg` |

**알려진 사항**

- 일부 문서를 열 때 엔진이 `LAYOUT_OVERFLOW: ...`를 stderr에 찍는다(진단 출력). API로는 끌 수 없으며 필요하면 Rust 쪽 변경이 필요하다.
- 디코딩은 actor의 전용 큐에서 동기로 한다. 디버그 빌드에서 약 80쪽을 파싱·디코딩하는 데 0.5초라 지금은 문제 없지만,
  큰 쪽(base64 그림)의 디코딩을 큐 밖으로 옮길지는 4단계에서 릴리스 빌드로 측정해 정한다.
- 미검증: 릴리스 빌드 성능, Xcode 앱 프로젝트에서의 패키지 소비, 이미지 `crop`·`fillMode`의 의미(필드만 모델링).

## 3단계: 앱 셸

읽기 전용 뷰어 앱 `RHWP`(`macos/App`)가 문서를 열고 쪽 썸네일 사이드바와 쪽 스크롤 영역으로 보여 준다.
빌드는 `macos/scripts/build-app.sh [--run <문서>]`(XCFramework → XcodeGen → xcodebuild, 임시 서명)다. 프로젝트·`Info.plist`·
권한 파일은 `project.yml`에서 생성하며 커밋하지 않는다.

**구성**

| 모듈 | 역할 |
| --- | --- |
| `RhwpKit` | `RhwpDocumentSession.pageSizes()` 추가. 모든 쪽의 크기를 한 번에 읽는 C ABI `rhwp_document_page_sizes`를 쓴다 |
| `RhwpRender` | `PageRenderer`: 레이어 트리 → CoreGraphics/CoreText. `RenderReport`가 그린/건너뛴 op와 글꼴 대체를 집계 |
| `RhwpViewer` | `Zoom`, `PageLayout`, `RenderScalePolicy`, `LRUCache`, `ViewerModel`(열기·배율·쪽 그림 캐시). UI에 의존하지 않는다 |
| `rhwp-render` | 한 쪽을 PNG/JSON으로 저장하는 도구(`macos/scripts/rhwp-render.sh`). 0단계 스파이크를 대체해 지웠다 |
| `macos/App` | SwiftUI 화면만 둔다: `DocumentGroup(viewing:)`, `NavigationSplitView`, 사이드바 `List`, `ScrollView`, 도구 막대, 보기 메뉴 |

**설계 결정**

- **화면은 시스템 컴포넌트만 쓴다.** `DocumentGroup`, `NavigationSplitView`, 사이드바 `List`, `ScrollView`, 도구 막대의
  `Button`·`Menu`다. Liquid Glass 도구 막대와 사이드바는 최신 SDK로 빌드하면 시스템이 입힌다. 직접 유리 효과를 그리지 않는다.
- **쪽 크기를 먼저 알고 배치를 먼저 정한다.** 쪽 그림이 늦게 도착해도 스크롤 길이가 흔들리지 않는다. 배치는 값(`PageLayout`)이고
  배율이 바뀌면 새로 만든다. 크기를 쪽마다 레이어 트리를 만들어 얻지 않고 조판 결과의 쪽 배치를 한 번에 읽는다.
- **그림은 화면에 나타나는 쪽만, 비동기로.** `LazyVStack`이 가까운 쪽만 만들고 `.task(id:)`가 배율이 바뀌면 다시 받고 화면에서
  사라지면 취소한다. 같은 쪽·배율의 동시 요청은 하나로 합치고(`inFlight`), 결과는 비용 상한(384MB)의 LRU에 둔다.
  그리기는 메인 액터와 문서 큐 밖(`Task.detached`)에서 한다.
- **모델을 앱이 아니라 패키지에 둔다.** `ViewerModel`은 SwiftUI에 의존하지 않는다. 앱 안에서 도는 시험은 샌드박스 때문에 저장소 샘플을
  읽을 수 없으므로, 모델을 `RhwpViewer`에 두어 샌드박스 없이 `swift test`로 실제 문서를 열어 검증한다.
- **너비 맞춤이 기본이고 직접 정하면 유지된다.** 열면 창 너비에 맞추고 창 크기가 바뀌면 따라간다. 확대·축소로 배율을 직접 정하면
  그 배율을 유지하고, "너비에 맞춤"을 누르면 다시 따라간다. 확대 단계는 `Zoom.steps`의 다음 단계라 맞춤 배율(단계에 없는 값)에서도
  한 번 누르면 달라진다.
- **UTI는 앱이 선언한다.** HWP·HWPX·HML은 시스템에 정해진 UTI가 없다(`io.github.jasontreksc.rhwp.{hwp,hwpx,hml}`을 내보낸다).
  한컴 오피스의 기본 앱 지정을 가로채지 않도록 핸들러 순위를 `Alternate`로 뒀다.
- **샌드박스를 켜 둔다**(`app-sandbox`, `files.user-selected.read-write`). 문서 앱의 기본 형태이고 10단계에서 새로 켤 때의 놀람을
  줄인다. 서명은 로컬용 임시 서명이며 배포 서명·공증은 10단계다.
- **렌더러 이식은 픽셀로 증명했다.** 스파이크의 동적 딕셔너리 렌더러를 모델 위로 옮겼고, 스파이크가 만든 참조 PNG 9장(5개 문서, 텍스트·표·
  그림·그라데이션·타원·경로 포함)과 출력이 **픽셀 단위로 모두 동일**하다. 달라진 규칙은 하나다: 선 전용 경로는 `PathOp.lineStyle`을
  `style`의 테두리보다 우선한다(모델 문서의 약속이며 스파이크의 병합 규칙은 엔진이 `style.strokeWidth`를 항상 보내서 선을 그리지 못했을 것이다).

**검증**

- Swift 시험 69건 통과: `RhwpKit` 22, `RhwpRender` 14, `RhwpViewer` 33. 기대 픽셀은 엔진 출력이 아니라 손으로 만든 트리로 정했다
  (채우기·배율·잘라내기·그라데이션 방향·`lineStyle`·엔진이 준 글자 위치). 실제 문서에서는 모든 op가 집계에 한 번씩 잡히는 불변식을 본다.
- 결함 주입(모두 검출·원복): 쪽 크기 가로·세로 뒤바꿈(Rust 시험), 잘라내기 제거, 그라데이션 시작·끝 뒤바꿈, 진행 중 요청 합치기 제거.
- 앱은 경고 없이 빌드(Swift 6 엄격 동시성)되고 HWP·HWPX·손상된 파일을 열어도 살아 있으며 크래시 리포트가 없다.
- 앱을 실제로 띄워 `KTX.hwp`를 연 화면을 한 번 확인했다: 제목, 쪽 썸네일 사이드바, 본문 쪽, `85%` 배율 메뉴, `1 / 27쪽`이 보였다.

**알려진 사항 / 4단계로 넘기는 것**

- 화면 상호작용(사이드바 선택 → 스크롤, 스크롤 → 사이드바 선택, 확대 단축키, 핀치)은 **화면에서 직접 확인하지 못했다.** 자동 입력은 접근성
  권한이 필요한데 승인하지 않았다. 논리(배치·배율·캐시)는 시험이 지키지만 SwiftUI 연결은 사람이 한 번 눌러 보아야 한다.
- 핀치 확대는 손을 뗄 때 한 번에 바뀐다. 제스처 중 실시간 확대와 타일링 렌더러는 4단계다. → 이월을 거쳐 [타일 렌더링과 뷰어](#타일-렌더링과-뷰어)에서 풀었다.
- 쪽 비트맵 한 변은 4096px로 제한한다(큰 배율에서는 선명도가 낮아진다). 타일링으로 푼다. → 같은 절에서 풀었다(상한을 없앴다).
- 렌더러가 아직 하지 않는 것(4단계에서 대부분 해결, 결과는 아래 4단계 절): 그림의 `crop`·`fillMode`·투명도·회전, 선의 회전, SVG 타원호의
  정확한 호, `tabLeader`·`textDecoration` 등 `.unsupported` op. 한컴 글꼴이 없어 대체 글꼴로 그리는 한계는 그대로다.
- 앱 아이콘, 현지화, 서명·공증은 10단계다.

## 4단계: 페이지 렌더러

"샘플 세트의 쪽별 일치율이 자동 측정됨"이 완료 기준이었다. 측정 도구를 먼저 만들고 그 수치를 보며 렌더러를 채웠다. **타일링 렌더러는
이번에 하지 않았다**(아래 "이월").

**측정 도구**

- `macos/scripts/fidelity-sweep.py --discover --pages 1-6`: `pdf/`의 한컴 PDF와 같은 이름의 `samples/` 문서 589쌍을 찾아 우리 렌더러
  (`rhwp-render <문서> --all`)와 한컴 PDF(`rhwp-render --pdf`, CGPDFDocument로 흰 배경에 래스터)의 쪽 PNG를 만들고
  `scripts/visual_sweep.py --silhouette-only --png-pair`로 쪽별 일치율을 낸다. 쪽수 불일치는 일치율과 따로 기록한다. 쪽별·문서별 TSV와
  건너뛴 op 종류별 평균 일치율, 대체된 글꼴 순위를 함께 낸다. 약 2.5분이 걸린다. 산출물은 git이 무시하는 `output/fidelity/`에 둔다.
- 도구를 만들며 고친 측정 오류 두 가지: ① `visual_sweep.py`는 한 쪽이라도 90% 미만이면 비정상 종료한다. 그걸 "비교 실패"로 치면 가장 나쁜
  문서가 빠져 평균이 97.5%로 부풀었다(성공은 `silhouette.tsv` 유무로 판정한다). ② 같은 이름의 문서·여러 PDF가 한 폴더에 겹쳐 쓰였다
  (결과 폴더 이름을 PDF 경로에서 만든다).

**결과** (같은 589쌍·1~6쪽·1,894쪽, 실루엣 일치율)

| 단계 | 평균 | 중앙값 | 90% 미만 쪽 |
| --- | --- | --- | --- |
| 기준선(3단계 렌더러) | 82.5% | 94.5% | 786 |
| + 수식·원본 SVG(차트)·양식·OLE 자리 표시·각주 표식, SVG 조각 렌더러 | 84.3% | 95.2% | 655 |
| + 글자 장식(밑줄·취소선·강조점)·탭 리더 | 84.6% | 95.6% | 632 |
| + 원형 그라데이션, 그림(잘라내기·채우기·SVG 그림), 정확한 호, 선 변환 | 86.2% | 95.7% | 596 |
| + 글꼴 대체 표 | 86.4% | 95.8% | 581 |
| + 회전 그림 틀·세로가 뒤집힌 잘라내기 수정(최종) | **86.4%** | **95.8%** | **579** |

최종 기준 1,315쪽이 90% 이상이다(기준선 1,108쪽). 1점 넘게 좋아진 쪽 552, 나빠진 쪽 23(아래 "남은 악화"). 건너뛴 op는 `charOverlap`(6개
문서), 그림 밝기·대비(5), 그레이스케일 효과(2), 무늬 칠(1)만 남았다.

**설계 결정**

- **정본은 엔진의 SVG 렌더러(`src/renderer/svg.rs`)다.** 장식·탭 리더·그림 채우기·수식 배율 규칙을 거기서 옮겼다. Swift에서 조판을 다시
  계산하지 않는다는 원칙은 지키지만 **그리기 규칙은 두 곳에 있게 된다**(중복 위험): 밑줄·취소선 기하, 선 모양 13종, 탭 리더 12종, 강조점,
  각주 표식 위치, 양식 개체 그리기, 그림 채우기·잘라내기 좌표 변환, 수식 배율, 수식·차트 SVG 부분집합. 엔진 쪽이 바뀌면 각 파일 머리의 목록을
  보고 같이 고친다. 이 중복을 없애는 길은 엔진이 이 규칙을 레이어 트리에 풀어 싣는 것이다(엔진 변경이라 별도 작업).
- **장식은 별도 op가 그린다.** 엔진은 `textRun`의 스타일에도 밑줄·취소선을 싣지만 이는 옛 경로의 거울이다. 두 곳에서 그리면 이중선이 되므로
  `drawTextRun`은 그리지 않는다(시험이 지킨다).
- **SVG 조각은 트리로 읽은 뒤 그린다.** 처음에는 `NSXMLParser`가 읽는 즉시 그렸는데, 그림 안의 SVG 그림(WMF/EMF를 엔진이 SVG로 바꾼 것,
  래스터를 감싼 SVG)을 그릴 때 파서가 다시 불려 `NSInternalInconsistencyException`으로 죽었다. 트리로 읽고 재귀로 그린다.
- **글꼴은 번들하지 않고 대체 표를 쓴다.** 한컴 글꼴은 라이선스상 번들할 수 없다. `FontSubstitution`이 `글꼴 이름 → 후보 목록` 표(정확한
  이름, 이름의 성격: 명조·고딕·궁서·헤드라인·고정폭, CSS 일반 가족)를 갖고, 설치된 첫 후보를 쓴다. 후보 순서를 일치율로 골랐다: 명조 계열은
  Nanum Myeongjo가 AppleMyungjo보다 평균 0.1점·90% 미만 4쪽 낫고, 고딕은 Apple SD Gothic Neo와 Nanum Gothic의 차이가 0.1점 이내여서
  모든 macOS에 있는 쪽을 앞에 뒀다. **글꼴 선택은 지렛대가 아니다**: 글자 위치는 엔진이 정하므로 글리프 모양이 다른 것만 남고, 후보를 바꿔도
  ±0.1점이다. 쉼표 목록(수식·차트 SVG의 `font-family`)도 같은 해석기로 푼다.
- **그림 규칙에서 엔진과 다르게 한 곳 하나.** 엔진은 잘라내기 선택이 비면(`right <= left || bottom <= top`) 그림을 그리지 않는다. 한컴
  PDF는 **세로가 뒤집힌** 선택(`bottom <= top`)에서 그림 전체를 그린다(`156564340-ip-dispute-mediation-poster-slice`의 로고, crop
  `(0, 6240, 304, 2619)`: 전체를 그리면 일치율 100%, 건너뛰면 79%). 그래서 세로가 빈 선택은 무시하고 전체를 그리고, **가로가 빈 선택만**
  그리지 않는다(가로가 빈 경우의 한컴 동작은 샘플에 자료가 없어 미검증).
- **90°·270° 회전 그림은 틀을 맞바꿔 그린다.** HWPX의 크기는 회전 후 외접 사각형이라 bbox 위에 회전을 또 적용하면 이중 회전이 된다.
  엔진의 `effective_image_bbox`와 같은 규칙이다. 이것을 빠뜨렸을 때 `picture_band_cell_spaces` 1쪽이 97.9%에서 82%로 떨어졌고, 고친 뒤
  97.9%로 돌아왔다(시험으로 고정).

## 타일 렌더링과 뷰어

4단계가 이월한 일이다. 지금까지 뷰어는 쪽 하나를 통째 비트맵 한 장으로 그리고 한 변을 4096px로 제한했다(`RenderScalePolicy`). 그래서 확대 4배
Retina(배율 8, A4가 6350×8980px)에서는 3.65배로 낮춰 그려 흐렸고, 핀치 확대는 손을 뗄 때 한 번에 바뀌었다. 이제 쪽을 타일로 나눠 보이는 곳만 그리고
핀치 중에는 지금 그려진 것을 즉시 늘여 보여 준다. 브랜치는 `feat/tiled-viewer`다.

**구성**

| 모듈 | 추가·변경 |
| --- | --- |
| `RhwpRender` | `PageRenderer.renderTile(_:scale:tile:)`(비트맵의 한 영역만 그린다), `TileGrid`·`TileIndex`·`PixelRect`(쪽 비트맵을 나누는 기하), `Culling`(타일 밖 op 건너뛰기). `draw(_:into:visibleRect:)`가 보이는 영역을 받는다 |
| `RhwpViewer` | `TilePlanner`(보이는 영역 → 타일), `ViewerModel`의 타일·레이어 트리 캐시·`renderPlan`·`loadTiles`, `Viewport`, `PinchState`, `PageLayout.point(matching:)`(확대 앵커) |
| `rhwp-render` | `--bench`: 쪽마다 엔진·디코딩·통째 렌더·타일 한 장의 시간과 메모리(릴리스 빌드로) |
| `macos/App` | `PageTilesView`(타일 `Image`들), `PageScrollView`(스크롤 지오메트리·핀치·스크롤 요청) |

**설계 결정**

- **타일은 컨텍스트를 정수 픽셀만 옮겨 그린다.** 통째 렌더의 변환은 `translate(0, H) · scale(s, −s)`이고, 타일은 `translate(−tx, th + ty) · scale(s, −s)`다.
  두 식의 차가 정수라서 모든 도형이 같은 부분 픽셀 위치에 놓인다. 격자의 비트맵 크기도 통째 렌더와 같은 올림 크기다.
- **타일 밖 op는 건너뛰되 "모르면 그린다".** CoreGraphics가 타일 밖 픽셀을 버려 주므로 건너뛰지 않아도 결과는 같고, 건너뛰는 것은 비용(글자를 CoreText로 다시
  배치하는 일이 타일 수만큼 곱해지는 것)을 줄이려는 것뿐이다. 근거는 둘이다. ① `clipRect`의 자식은 그 사각형 안에서만 보인다(엔진 `bounds`와 무관한 사실).
  ② 잎 op의 범위를 그리기 매개변수에서 보수적으로 잡는다(글자는 bbox가 아니라 원점·글자 위치·크기·장평에서, 회전은 외접 정사각형으로, 선·경로는 굵기와
  제어점을 더해). **그룹 `bounds`는 쓰지 않는다**: 엔진이 렌더 트리 노드 bbox를 그대로 싣는 것이라 자식이 그 안에 있다는 보장이 없다. 회전·세로쓰기 글자와
  모르는 op는 판단하지 않고 그린다.
- **캐시 단위는 둘이다.** (1) 디코딩한 `PageLayerTree`는 쪽당 하나(JSON 바이트 × 5를 비용으로 96MB LRU). 한 쪽의 타일 수십 장과 배율 변경이 같은 트리를 쓰므로
  타일마다 엔진 호출과 JSON 디코딩을 되풀이하지 않는다. (2) 비트맵은 `RenderKey(쪽, 배율, 타일 번호)`로 기존 384MB LRU에 둔다(타일 번호가 없으면 쪽 전체 한
  장: 썸네일과 흐린 밑그림). 같은 키·같은 쪽의 동시 요청은 하나로 합치고, 요청한 쪽이 취소돼도 시작한 일은 끝까지 가서 캐시에 남는다. 문서를 다시 열면
  `epoch`가 올라가 이전 문서의 늦은 결과가 새 캐시에 들어오지 않는다.
- **타일 요청은 창을 두고 가까운 것부터, 취소하면 멈춘다.** `loadTiles`는 동시에 3장만 시작하고 취소되면 아직 시작하지 않은 타일을 시작하지 않는다. 스크롤로
  지나친 쪽의 타일 수십 장이 줄을 서서 CPU를 먹지 않게 하려는 것이다. 보이는 영역의 중심에 가까운 타일부터 그린다.
- **새 배율의 타일이 오기 전에는 이전 배율의 타일이 밑에 깔린다.** `renderPlan`이 캐시에 남은 다른 배율의 타일(가까운 세 배율, 먼 것부터)을 정확한 배율의
  타일 뒤에 놓는다. 확대한 직후 흰 종이 대신 이전 해상도의 그림이 보인다. 그 밑에는 쪽 전체의 흐린 밑그림(긴 변 1024px)이 있다.
- **디코딩은 문서 큐 밖에서 한다(④의 결정).** 엔진 호출(JSON 생성)만 문서 큐에서 하고 `PageLayerTree.decode`는 큐 밖의 작업에서 한다. 큐는 문서 하나의 모든
  엔진 호출이 줄 서는 곳인데, 디코딩은 순수 CPU 일이고 아래 측정에서 엔진 시간의 62%였다.
- **핀치는 제스처 중에 배율·배치·타일을 바꾸지 않는다.** `PinchState`가 비율(`base × 비율`이 `Zoom.range` 안에 들도록 맞춤)만 들고, 화면이 `scaleEffect`로 지금
  그려진 것을 늘여 보여 준다(이미 그려진 타일을 늘이므로 흐리다). 손을 떼면 `setZoom`이 새 배율을 정하고 위의 이전 타일 밑그림이 새 타일이 올 때까지 채운다.
  0.5% 이하의 변화는 무시해 손가락 떨림이 너비 맞춤을 끄지 않게 했다.
- **확대할 때 붙잡은 곳이 같은 자리에 머문다.** 핀치는 손가락 중심, 확대·축소 명령은 보이는 영역 중심, 창 크기에 따른 너비 맞춤은 맨 위를 붙잡는다.
  `PageLayout.point(matching:in:)`가 점을 쪽 안의 비율로 옮기고(쪽 사이 간격·여백은 배율과 무관한 고정 길이로 둔다) 모델이 `ScrollRequest`로 화면에 스크롤을
  요청한다.
- **화면은 타일마다 `Image` 뷰를 쓰고 `Canvas` 한 장에 그리지 않는다.** `Canvas`는 자기 크기만큼 백킹 스토어를 잡는다. 배율 8의 쪽 하나는 6350×8980px(228MB)라 타일로
  나눈 이득이 사라진다. `Image`는 `CGImage`가 그대로 레이어 내용이 되어 타일 하나(1MB)만큼만 든다. UI는 SwiftUI 시스템 컴포넌트뿐이다.
- **macOS 26의 스크롤 인셋.** 상세 화면의 스크롤 영역은 도구 막대와 떠 있는 사이드바 **아래까지** 이어져서 `contentOffset`이 쉴 때 (−176, −52)로 보고된다.
  처음에는 이 값을 그대로 모델에 줘서 확대 앵커가 항상 0으로 막혔다(앱을 실제로 띄워 보고서야 알았다). 화면이 인셋을 더해 가려지지 않은 영역의 왼쪽 위(`Viewport.offset`)로
  바꿔 넘기고, 타일은 가려진 곳까지 덮도록 `Viewport.insets`를 함께 싣는다. `ScrollPosition.scrollTo`의 좌표도 이 보정한 공간이다(요청 (58.85, 37.6) → 보고 (59.0, 37.5)).

**타일 합성과 통째 렌더의 픽셀 비교** (이 절이 "타일 합성이 통째 렌더와 같은 픽셀"의 정확한 의미다)

타일을 이어 붙인 비트맵과 통째로 그린 비트맵은 **내용에 따라 비트 단위로 같거나 몇 단계 다르다.**

| 내용 | 결과 | 관측 |
| --- | --- | --- |
| 축에 나란한 도형(소수 좌표·테두리 포함), 가로·세로선, 90° 회전, 반투명, 글자, 그림(리샘플링), 잘라내기 | **비트 단위로 같다** | 배율 0.5·1·1.37·2.5, 타일 37·64·512px 9가지에서 다른 픽셀 0 |
| 점선, 그라데이션, 타원·둥근 모서리 | 최대 1단계 | 8비트 덮임이 한 칸 반올림되는 차이 |
| 기울어진 변(대각선, 임의 각도 회전, 삼각형, 큰 곡선) | 최대 15단계 | 대각선 15, 30° 회전 사각형 7, 큰 곡선 5, 삼각형 4 |

원인은 **위치가 아니라 컨텍스트 크기**다. 같은 크기의 비트맵 안에서 정수 픽셀만큼 옮겨 그리면(1·7·64·512·1000px) 비트 단위로 같다(탐침). 타일 컨텍스트는 통째
비트맵보다 작아서 CoreGraphics가 비직선 도형·그라데이션을 래스터할 범위를 다르게 잡는다. 차이는 타일 가장자리가 아니라 타일 안쪽에 고르게 퍼져 있어 이음매 줄이 아니다.

**그리고 어긋난 쪽은 통째 렌더다.** 어긋난 픽셀을 해석적 덮임(선분이 픽셀을 덮는 비율을 16×16 부분 표본으로 계산)과 견주면 타일이 정답에 더 가깝다.

| 시험 | 어긋난 픽셀의 평균 오차 (통째 / 타일) |
| --- | --- |
| 대각선 @1, 타일 64 | 0.0117 / 0.0049 |
| 대각선 @2.5, 타일 64 | 0.0140 / 0.0021 |
| 대각선 @14(4200×2800), 타일 512 | **0.1305 / 0.0134**, 통째 렌더는 해석 111인 픽셀을 255로 칠한다 |

긴 대각선에서 CoreGraphics가 큰 비트맵을 통째로 그릴 때가 덜 정밀하다. 그래서 기울어진 변의 기준은 통째 렌더가 아니라 해석적 기하다(허용 오차 0.1은 부분 표본
오차 ±0.03과 선 끝 모서리의 작은 덮임(0.1 이하)을 8비트에서 버리는 차이(관측 0.082)를 합친 값이다). 통째 렌더와의 비교 한도(곡선·그라데이션 2단계, 기울어진 변 16단계)는
관측 위에 둔 상한이며, 타일 이동이 1px만 틀려도 글자·직선 가장자리에서 100 넘게 어긋나므로 정확-동일 묶음이 그것을 잡는다.

| 항목 | 중앙값 | p90 | p99 | 최대 |

| JSON 크기(KB) | 399 | 817 | 2,344 | 7,584 |

  그래서 문서 큐 밖으로 옮겼다. 큐 안에서 하면 같은 문서의 다른 쪽 요청이 그 시간만큼 기다린다.
- 트리 메모리는 JSON의 0.9~4.5배였다(JSON 1MB 넘는 쪽 12건; 표가 큰 쪽이 4배 넘고 그림이 큰 쪽이 1배 안팎). 캐시 비용을 JSON × 5로 어림한 근거다. 측정은 `phys_footprint`
  차이라 잡음이 있다.
- 타일 한 장의 최댓값 386ms는 한 문서(`3-11월_실전_통합_2024-…`)에서 나왔고 그 쪽의 통째 렌더(194ms)보다 길다. 가운데 타일이 그 문서의 첫 그리기라 글꼴 해석 비용이 든
  것으로 **추정**한다(확인하지 않았다). 나머지는 모두 통째 렌더보다 짧다.
- **배율 8(확대 4배 Retina)의 큰 쪽**:

| 쪽 | 비트맵 | 통째 렌더 | 타일 한 장 | 통째 렌더의 메모리 증가 | 같은 크기 한 장의 명목 크기 |
| --- | --- | --- | --- | --- | --- |
| `exam_eng` 4쪽 | 8981×12699 | 244ms | 19.7ms | 112.8MB | 456MB |
| `multi-table-002` 2쪽 | 6350×8981 | 68.5ms | 7.9ms | 59.7MB | 228MB |

  통째 렌더의 증가분이 명목 크기보다 작은 것은 흰 바탕의 쪽이 대부분 건드려지지 않은 채 압축되기 때문이다(`phys_footprint` 기준). 타일은 한 장 1MB이고 화면에는 보이는 곳의
  수십 장(+여유 반 타일)만 필요하다. 한 변 16384px를 넘는 쪽은 통째 렌더가 아예 거부하지만(시험 `tileFarFromTheOrigin`: 300×200 쪽 @60배 = 18000×12000px) 타일은 그린다.

**알려진 사항 / 미검증**

- **핀치 제스처는 화면에서 확인하지 못했다.** 자동 입력으로 `MagnifyGesture`를 만들 수 없었다. `PinchState`·`pinchChanged/Ended`·확대 앵커는 모델 시험이 지키지만 SwiftUI 연결(`scaleEffect`,
  손을 뗄 때 배치·스크롤 요청이 한 프레임 어긋나 깜박이는지)은 사람이 한 번 만져 보아야 한다. 자동 입력을 마치기 전, 내가 보내지 않은 입력으로 확대 라벨이 400% → 74% → 48%로 내려갔다
  (마우스 커서도 내가 둔 자리가 아니었다). 사용자가 직접 핀치한 것으로 보이지만 확인하지는 못했다.
- 사이드바 이동의 가로 위치 수정은 고친 뒤 화면에서 다시 확인하지 못했다. 창 크기를 바꿀 때의 너비 맞춤 앵커(맨 위 붙잡기)도 화면에서 보지 못했다(모델 시험은 있다).
- 타일 이음매는 400%·74%·48%의 스크린샷에서 줄이 보이지 않았다(눈으로 본 것이며 자동 검사가 아니다). 타일 경계가 장치 픽셀에 놓이지 않는 경우(`zoom / scale ≠ 1/화면 배율`, 즉 상한 때문에
  배율이 낮아진 아주 큰 쪽)와 Retina가 아닌 화면은 확인하지 않았다.
- **걸러내기(`Culling`)의 안전은 경험적이다.** 근거 둘(`clipRect`, 그리기 매개변수에서 구한 범위)은 논증이지만, 잎 op의 여백(24px)은 "엔진이 bbox 밖으로 그리는 양이 이보다 작다"는 가정이다. 합성
  입력과 실제 쪽 12장에서 걸러낸 타일과 걸러내지 않은 타일이 비트 단위로 같았고, 샘플 전체의 타일 대조는 하지 않았다. 샘플 전체에서 `fidelity-sweep.py`를 타일 경로로 돌려 보는 것이 남은 확인이다.
- 측정은 1~4쪽만 훑었다(문서 371개, 866쪽). 긴 문서의 뒤쪽 쪽이나 그림이 많은 쪽의 분포는 다를 수 있다. 메모리는 `phys_footprint` 차이라 잡음이 있다.
- 화면에 보이는 타일 수·여유(반 타일)·동시 시작 수(3)·타일 크기(512px)는 측정으로 고른 값이 아니라 합리적인 초기값이다. 바꾸는 근거는 실제 앱의 스크롤 체감 측정이 필요하다.
- 다음 단계(5단계 뷰어 기능)에서 찾기·하이퍼링크가 들어오면 `renderPlan`의 밑그림 층 위에 얹는 요소(선택·강조)가 필요하다.

- **렌더 충실도**: 4단계에서 평균 82.5% → 86.4%, 90% 미만 쪽 786 → 579로 올렸다. 남은 차이는 한컴 글꼴 부재(글리프 모양)와 엔진 규칙·조판 쪽(탭 리더, 쪽수 불일치)이다.
- **편집 후 증분 렌더**: 스파이크는 쪽마다 문서를 다시 파싱했다. 핸들 기반 API에서 편집 후 쪽 단위
  무효화와 레이어 트리 캐시를 쓰는 경로(`wasm_api`가 이미 사용 중)를 따라야 한다.
- **Rust 조판 변경**: 조판을 건드리게 되면 저장소의 Visual Sweep·90% 게이트가 그대로 적용된다.
  이 포크의 Swift 작업은 가능한 한 Rust 조판 코드를 수정하지 않는다.
- **라이선스**: 번들 글꼴과 한컴 글꼴 취급은 10단계 이전에 확인한다.
